# 交易订单生命周期

本文记录当前系统的开仓、加仓、减仓、清仓和自动止损规则。目标是让代码、日志、
`ttt_order_events` 与 Alpaca 券商状态使用同一套口径。

## 1. 基本原则

1. Alpaca 是订单和成交的事实来源；`submit` 只表示券商受理，不表示成交。
2. `ttt_order_events` 是本系统逐笔订单事件的事实表。`ttt_trades` 是根据已成交事件
   重算出来的持仓生命周期投影，不再把另一份本地“交易记录”当事实来源。
3. 本地 `ManagedPosition` 是运行时投影，只能由券商确认的累计 `filled_qty` 和
   `filled_avg_price` 更新。
4. 订单归属只认 `client_order_id` 的 `ttt-` 前缀。平仓前撤本系统同合约全部在途单
   （包括尚未成交的加仓买单，防止平仓后重新暴露仓位），不撤人工订单或其他系统订单。
5. 期权订单使用 `DAY` 限价单，并明确发送：
   - 买入：`buy_to_open`
   - 卖出：`sell_to_close`
6. 每次新订单使用唯一 `client_order_id`。如果以后增加网络自动重试，同一次业务下单
   必须复用原 ID，不能生成新 ID 后盲目重下。
7. 买入时必须选择一个价格止损模式：`percent`（默认）或 `amount`。两个阈值来自纪律模板，
   下单面板只允许选择模式，不允许修改数值；选择结果随持仓冻结。
8. `DATA_SOURCE=mock` 或本机 MOCK Alpaca endpoint 产生的生命周期仍完整落库，但必须标记
   `source=mock`；它们不进入 PAPER 的交易次数、连亏和冷却统计。

以上订单字段遵循 Alpaca 官方接口定义：
[Alpaca MCP Server](https://docs.alpaca.markets/us/docs/alpaca-mcp-server)。
其中“穿价几档、等待多久、重试几次”是本系统的执行策略，不是 Alpaca 官方保证。

## 2. 数据职责

### `ttt_order_events`

每一个真实券商订单一条记录，保留：

- `order_id`、`client_order_id`、`parent_order_id`
- `origin`：`user`、`system`、`external`
- `action`：`open`、`add`、`reduce`、`close`、`auto_close`
- `side`、委托数量、价格类型、限价
- 券商状态、实际成交数量、实际成交均价、失败或撤单原因
- watchdog 自动平仓首单额外冻结 `triggered_at`、触发 bid/ask、触发价值/亏损、
  `stop_mode`、`stop_threshold` 和 `entry_value`

同一次追价产生三张订单，就记录三张订单，不能只保留最后一张。触发快照只写第一张
`auto_close` 卖单，后续追价单通过同一个 `parent_order_id` 关联，避免重复快照。

### `ttt_trades`

这是供持仓列表、统计和复盘读取的投影：

- 所有已成交买单按数量和真实成交均价加权形成成本；
- 所有已成交卖单按数量和真实成交均价计算已实现盈亏；
- 未成交、已拒绝或未成交撤单不改变持仓；
- 部分成交只按已成交数量计算。

统计应从 `ttt_order_events` 重算或校验 `ttt_trades`，不能混用报价 mid、委托价和成交价。
真实纪律统计只读取 `source <> 'mock'` 的生命周期；切回 PAPER 不需要清空 MOCK 复盘记录。

## 3. 开仓

1. 通过信号、市场状态、资金和仓位等闸门。
2. 选择止损模式；未显式选择时默认 `percent`。模板中的百分比、金额和最长持仓时间不可由
   本次订单请求覆盖。
3. 使用最新报价计算限价，提交 `buy_to_open`。
4. 立即写一条 `pending/open` 订单事件，但持仓仍是 `pending`。
5. TradingStream 到达后优先消费；REST 定时对账和断线恢复作为补充。
6. 只有同时取得 `filled_qty > 0` 和 `filled_avg_price`，才把真实成交应用到持仓并启用止损。
7. 如果 WS 只给成交数量、没有均价，立即向 REST 补查；仍取不到时保持 `pending`，
   绝不能拿选约 mid 或委托价冒充真实成本。
8. 原始开仓单后续从部分成交继续增加时，只应用累计成交量相对上次的增量，不能覆盖已经
   包含加仓的总持仓。
9. 同一 OCC 合约已经存在 `pending/open/closing` 生命周期时，新的“开仓”请求必须在提交
   券商前拒绝；需要增加数量只能走“加仓”。检查与券商提交、本地登记必须由同一把合约锁
   串行保护，不能依赖前端防抖，也不能让后一次开仓覆盖前一次持仓。

## 4. 加仓

1. 加仓仍属于新增风险，必须经过适用的风险闸门和同标的仓位上限检查。
2. 提交 `buy_to_open` 后只写 `pending/add` 事件，不立即增加本地数量。
3. 收到券商累计成交后，计算：

   `新增应用量 = 本次累计 filled_qty - 已应用累计量`

4. 用“累计成交名义额减去已应用名义额”计算新增部分的真实均价，再更新持仓加权成本；
   不能直接把最新累计均价当作新增部分均价。
5. 同步 `submit` 回包与 TradingStream/REST 可能同时看见同一成交；成交增量必须先原子认领，
   只有认领成功的一方可以更新持仓，禁止重复加仓。
6. 部分成交时先应用已经成交的部分；剩余部分继续等待最终成交或撤单终态。
7. Alpaca TradingStream 可能先确认成交，账户级 positions REST 随后才聚合出新张数。
   本系统确认买入后的 5 秒内，若 REST 仍返回较小的旧数量，只记录“等待快照追上”，
   不得用旧快照覆盖新成交；宽限期结束后仍不一致，才按券商真仓向下校正。

## 5. 减仓与清仓

1. 同一持仓进入 `closing` 后，新的重复平仓请求不再创建第二组卖单。
2. 平仓前只撤 `client_order_id=ttt-*` 的同合约在途订单，并逐笔等待 Alpaca
   `canceled/filled/...` 终态。撤单调用失败、仍为 `pending_cancel`、清理期间发生任何成交、
   出现替换单或清理后仍有程序挂单时，停止提交新卖单并先完成订单结算/持仓对账。
   若同一动作链已通过单笔查单或 TradingStream 确认某个订单 ID 进入终态，而 OPEN 列表
   短暂仍返回该 ID，只忽略这个有逐笔终态证据的 ID；其他程序单与外部单仍然阻断。
   进程恢复后即使本地已丢失某张 `ttt-*` 卖单与持仓的绑定，原子平仓仍会从 Alpaca OPEN
   查询发现并逐笔撤销该程序单、等待单笔终态；不能只报错后永久停在保护态。
3. 卖出明确使用 `sell_to_close`，不使用裸市价单。
4. 显式限价、非 `bid` 价格类型或关闭追价时，只发一张订单；未确认成交就显示
   `resting/closing`，不能谎报已平仓。
5. 默认主动平仓采用有界追价；watchdog 止损首手使用触发当刻的盘口：
   - 止损首手直接以触发 bid 提交，不重复发 REST 取第二份报价，也不主动压到 bid 以下；
   - 首手未成交时，后续手重新取得最新 bid/ask，并按 spread 有界加深；
   - 每手超时后请求撤余量，只有券商确认旧单进入终态后才提交下一手；
   - 每次提交数量是“请求数量减去本系统前面各手的已成交量”。
6. 成交确认只看每张本系统订单自己的累计 `filled_qty`。账户总持仓减少可能来自人工或
   其他系统，不能据此认定本单成交。
7. 多手部分成交的总退出价按成交量加权：

   `总退出均价 = Σ(每手成交均价 × 每手成交量) / Σ成交量`

   每张订单保存券商累计成交量和可后补的累计均价；相同累计量的后续帧补到均价时必须
   重新计算。只要任一已成交部分仍缺真实均价，整笔退出均价保持未知，不能用盘口 mid、
   委托价或把未知部分按 0 参与计算。
8. 追价耗尽或返回 `resting` 但已有部分成交时，立即按真实成交量扣减持仓、记录已实现
   数量；最后一张在途单以 `current_order_qty/current_order_filled_qty` 建立幂等跟踪，
   watchdog 后续只应用累计量相对 `close_applied_qty` 的新增部分。无真实均价时已实现
   盈亏价格保持未知。未成交余仓
   回到 `open`，下一次可以继续平仓。不能把整笔请求量都算成最后一手的成交价。
9. 撤单失败或仍处于 `pending_cancel` 时停止重挂，并继续追踪旧单；禁止让旧单与新单
   同时在场，从而避免超卖。

## 6. 自动止损

活跃持仓的每一帧期权报价都会唤醒止损判断；一秒定时拍只作为 WS 无更新或断线时的兜底。
新开仓闸门全部 BAN 时，候选合约可以释放订阅并从中间选约区消失，但所有
`pending/open/closing` 持仓合约仍由独立的 `positions` 高优先级 scope 强制订阅，
不受 BAN、候选预算或中间区域展示状态影响。持仓列表始终显示按最新 bid 计算的“市场价”
（实际可卖出价）；报价暂缺时显示 `—`，不拿入场价冒充实时价。
止损使用可变现口径计算：

- 成本：真实买入成交均价 × 100 × 当前数量；
- 当前价值：最新 bid × 100 × 当前数量；
- 未实现盈亏：当前价值减成本。

每个持仓始终启用最大持仓时间，到时不论盈亏直接清仓。价格止损严格二选一：

- `percent`：只检查冻结的亏损百分比，默认模式；
- `amount`：只检查冻结的美元亏损金额。

未选中的价格止损完全不参与判断。时间退出优先检查且不依赖期权报价：即使行情源暂时取不到
bid/ask，到达最长持仓时间仍必须开始平仓。进入 `closing` 采用原子状态切换，手动平仓和
watchdog 只有一方能取得执行权，不能发第二组单。加仓沿用原持仓模式，不允许借加仓切换。

金额止损的含义是“发现可变现亏损已达到阈值时立即发单”，不是保证最终亏损恰好等于阈值。
最终损失还包含：

- 相邻两帧报价之间的价格跳空；
- bid/ask spread；
- 下单、撮合和网络耗时；
- 首手未成交后为保证退出而采用的后续追价；
- 下单后的继续行情变化。

因此复盘必须分别记录并比较：

- `trigger_pnl`：触发拍按 bid 算出的盈亏；
- `first_limit_price`：第一手止损委托价；
- 每手提交和成交时间；
- 每手实际成交均价；
- `final_realized_pnl`。

这样才能区分“阈值计算错误”“检测延迟”“盘口 spread”和“成交滑点”。

## 7. 恢复与对账

1. TradingStream 负责实时增量，REST 负责启动基线、断线窗口和周期校验。
2. WS 和 REST 都可能重复返回累计成交；应用成交必须幂等。
3. TradingStream 回调只更新内存读模型并把订单 ID 投递到容量为 1024 的有界持久化队列；
   单 worker 串行落库，同一订单的待保存 revision 会合并。队列满或未初始化时会计数并
   限频告警，不能让数据库往返阻塞 alpaca-py 对后续 `trade_updates` 的顺序消费，也不能
   让数据库故障造成内存无上限增长。
4. 进程重启时先从 `ttt_order_events` 恢复订单事件，再从事件投影恢复交易状态。
5. 已经落库并投影过的终态事件在重启后视为已应用，避免再次加仓或减仓。
6. 对账优先按可信订单链计算本系统净持仓：
   `Σ(ttt 买入成交量) - Σ(ttt 卖出成交量)`。根开仓必须同时满足
   `client_order_id=ttt-*`、`origin=user|program|system`、`action=open`，并且能匹配
   `ttt_trades` 根行；不能仅凭账户里存在同合约持仓就认定归属。
7. 如果逐笔事件证明本系统净持仓大于 0，即使 `ttt_trades` 曾被竞态误标为 `closed`，
   对账也要按 `min(事件净持仓, 券商真实持仓)` 恢复；券商多出的数量仍视为外部仓。
8. 恢复误关生命周期时保留已实现盈亏，清除错误的全平时间、全平均价和总盈亏字段，
   重新标记为 `open`；最终卖完后再由全部逐笔事件重算真实结果。
9. 外部订单可以用于账户对账和展示，但不写成本系统策略成交，也不由本系统自动撤销。
10. 恢复持仓的在途平仓绑定必须同时满足：同一 OCC 合约、同一根开仓
    `parent_order_id`、唯一 pending SELL 候选，并由 Alpaca 单笔查询确认订单 ID、
    合约、卖出方向、`client_order_id=ttt-*` 和在途状态。候选不唯一或任一字段不符时
    不得猜测绑定。
11. 恢复时 Alpaca 当前持仓已经扣除了重启前的部分卖出成交，因此把该卖单当前
    `filled_qty` 设为 `close_applied_qty` 基线；后续只应用新增累计成交，不能重复减仓。
12. 前端撤单必须携带当前持仓绑定的精确 Alpaca 订单 ID；强刷后的临时绑定也必须满足
    唯一程序卖单和精确父订单条件，不得按 ticker、合约首单或数组顺序回退。
13. `closed/cancelled` 的内存历史记录不等于当前受管持仓，不得阻止同合约真实孤儿仓进入
    对账。判断“已登记合约”只看 `pending/open/closing`。
14. 风控平仓清理多张旧程序单时，先发送全部撤单请求，再在单一共享截止时间内轮询；
    总等待不随旧单数量增加，任一旧单未进入 Alpaca 终态仍会阻断新卖单。
15. 买入成交后的 5 秒内，如果 Alpaca positions REST 快照小于 `trade_updates` 已确认的
    本程序持仓，watchdog 风控平仓会临时以后者为数量下界；宽限期结束后恢复完全采用
    券商快照，且外部卖单冲突与撤单清理规则保持不变。

## 8. 禁止事项

- 禁止把 `submit`、持仓数量变化或 HTTP 200 当成交确认。
- 禁止用选约 mid、委托 limit 或最后一手成交价替代整笔真实加权成交价。
- 禁止平仓时批量撤掉同合约的外部订单。
- 禁止在加仓提交后、成交前修改本地仓位。
- 禁止用“再次开仓”代替同合约加仓，或让两条开仓生命周期共享一个合约注册槽。
- 禁止用 `ttt_trades` 和另一套本地交易记录分别做统计事实源。
